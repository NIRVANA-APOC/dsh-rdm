# dsh-rdm 0.2.0 — the Agent-native downloader

Status: **implementation contract** for `dsh-rdm-0.2.0`. Kernel, host and client
implement against this file; when reality disagrees, this file is updated first.

Scope: kernel (Rust), host plugin (TypeScript), model-facing tools, host browser
API, client review UI, docs. The shipped prebuilt kernels and all five platform
targets must stay buildable.

Previous design history: [`../ARCHITECTURE.md`](../ARCHITECTURE.md) (0.1.x),
[`../OPTIMIZATION.md`](../OPTIMIZATION.md) (measured 0.1.2 pass),
[`../../.design/DESIGN.md`](../../.design/DESIGN.md) (0.1.x panel).

---

## 1. Why this release exists

`dsh-rdm` is not a human download manager that happens to be scriptable. It is a
downloader whose **operator is an agent** and whose **auditor is a human**. Every
decision below follows from that split.

### 1.1 The agent's decision loop

An agent that wants a file has to answer, in order:

| Step | Question | What 0.1.x gave it | What it needs instead |
|---|---|---|---|
| discover | is this URL usable at all? | one probe with 8 fields | server facts, expiry, redirect chain, resume safety, learned origin history, a recommendation |
| decide | how should I fetch it? | nothing; fixed defaults | connections/chunk/single-stream recommendation plus the reasons |
| start | begin the transfer | task id + status | task id plus immediate preflight facts, one call |
| observe | what is happening now? | one EWMA byte rate | now + 1s/5s/30s/300s rates, trend, stall time, ETA confidence, workers, retries |
| intervene | should I pause/retry/wait? | status only | diagnosis + concrete next actions, machine-readable |
| verify | is the result trustworthy? | sha256 when it was requested | expected/actual/verified, server checksum availability, resume validator match |
| report | what do I tell the user? | free text | a bounded receipt the agent can quote |

### 1.2 The human's job

The human reviews. They do not compose downloads, tune connections or babysit
progress bars. They need:

* **global review** — one left-sidebar page answering "what is the machine doing,
  and did any download go wrong or become risky?";
* **session review** — one tab in the session's right sidebar answering "what did
  *this* agent download, and can I trust it?";
* **inline evidence** — the agent's tool calls in the conversation render small
  review cards, so review can happen without leaving the transcript;
* **no operations they must perform** — no URL composer, no connection sliders;
  only low-risk reveal/copy and an optional stop.

### 1.3 Principles

1. **Information over control.** Prefer telling the agent what the server does and
   what the transfer is doing over adding knobs. Defaults must be right.
2. **Progressive disclosure.** The polled hot path (list/notification) is flat and
   cheap; the one-shot detail path carries the heavy facts. Never ship full server
   facts in every notification.
3. **Bounded, stable, parseable.** Every canonical value has fixed keys and hard
   caps; every render is a line-oriented receipt with `key=value` fields, not
   human prose. No marketing adjectives.
4. **One fact, one place.** Policy lives in the system-prompt section; tool
   descriptions state behavior; parameter rules live on parameters. This follows
   the harness `agent-experience` guidance and cuts first-turn prompt tokens.
5. **Actionable failure.** Errors are `code` + `message` + optional `hint` +
   `actions`; the model should never need to guess what to do next.
6. **Session-native.** A download requested by an agent belongs to that agent's
   session; review surfaces are scoped by session. Global views aggregate, never
   blur.
7. **Honest telemetry.** Report what is measured (windowed bytes/time), mark
   unknowns `null`, never fabricate ETA confidence or verification.
8. **Review-first UI.** The UI's primary job is evidence presentation. Live motion
   is limited to one element (the throughput waveform head); everything else is a
   quiet ledger with an expandable evidence drawer.

## 2. Protocol v2 (kernel ⇄ host)

NDJSON transport and envelope are unchanged (`{"id",method,params}` /
`{"id",ok,result}` / `{"id",ok:false,error}`). `protocol` becomes **2**; the kernel
crate version becomes **1.1.0**. No compatibility with protocol 1 binaries is
promised: the host refuses a kernel whose ready frame reports protocol ≠ 2 with a
clear error.

### 2.1 `ServerFacts` (result of `probe`, also stored on a task)

```jsonc
{
  "url": "https://cdn.example.com/app.zip?sig=...",     // requested URL (credential query values redacted canonically)
  "finalUrl": "https://cdn.example.com/app.zip?sig=...", // after redirects
  "host": "cdn.example.com",
  "httpVersion": "HTTP/2.0",
  "status": 200,

  "fileName": "app.zip",
  "fileNameSource": "content-disposition" | "url",
  "totalBytes": 50406400,            // null when unknown
  "contentType": "application/zip",  // null when absent
  "contentEncoding": "gzip",         // null when absent
  "contentDisposition": "attachment; filename=\"app.zip\"",

  "range": {
    "supported": true,
    "acceptRanges": "bytes" | "none" | "unknown",   // raw header, trimmed
    "ifRange": true,                                // true only when a STRONG If-Range validator exists (strong ETag; never W/ or Last-Modified-only)
    "probedBy": "head" | "range-get",
    "probeStatus": 206,                             // status of the proving request, null for HEAD
    "probeBytes": 64                                 // bytes read while proving ranges
  },
  "validators": {
    "etag": "\"9b2cf5\"",       // null when absent
    "strongEtag": true,          // ETag present and not W/
    "lastModified": "Wed, 21 Oct 2026 07:28:00 GMT"
  },
  "resume": {
    "possible": true,
    "safety": "strong" | "weak" | "none",
    "reason": "strong-etag" | "last-modified-only" | "no-validators" | "no-range-support"
  },

  "signedUrl": {
    "signed": true,
    "expiresAt": 1763000123000,   // ms epoch, null when not derivable
    "expiresInSecs": 1180,        // negative when expired
    "source": "aws-sigv4" | "aws-sigv2" | "gcs-sigv4" | "azure-sas" | "generic-expires" | "unknown",
    "state": "valid" | "expiring" | "expired" | "unknown"
  },
  "tls": {
    "https": true,
    "notAfter": 1767000000000,    // ms epoch
    "expiresInSecs": 3456000,
    "issuer": "R11",              // CN or O; may be null
    "subject": "cdn.example.com", // CN; may be null
    "state": "valid" | "expiring" | "expired" | "unknown"
  },                              // null for plain http or when the cert cannot be read

  "redirects": [ { "status": 301, "url": "https://cdn2.example.com/app.zip" } ],
  "headers": {
    "server": "nginx",
    "date": "Wed, 21 Oct 2026 07:28:00 GMT",
    "cacheControl": "max-age=3600",
    "expires": null,
    "vary": "Accept-Encoding"
  },
  "rateLimit": {
    "retryAfterSecs": null,
    "limit": null,
    "remaining": null
  },
  "timing": {
    "probeMs": 84,
    "ttfbMs": 61,
    "sampleBps": 12345678   // null; filled only when a range probe actually read bytes
  },
  "checksum": {             // headers that would let the server prove integrity
    "contentDigest": null,   // RFC 9530 Content-Digest header
    "contentMd5": null,      // Content-MD5 (weak, legacy)
    "sha256": null,          // x-amz-checksum-sha256 only (whole-object when stored with it)
    "crc32c": null           // x-amz-checksum-crc32c / x-goog-hash crc32c
  },
  "warnings": ["weak-validators", "signed-url-expiring"],
  "recommendation": {
    "start": "now" | "later" | "avoid",
    "connections": 8,
    "chunkSizeBytes": 1572864,  // null = kernel auto
    "singleStream": false,
    "reason": "ranges+strong-etag",
    "verify": "recommended" | "required" | "unavailable"
  },
  "origin": {                 // learned ledger for this host, null when never seen
    "known": true,
    "attempts": 3,
    "completed": 2,
    "medianBps": 14680064,
    "bestBps": 23068672,
    "lastError": "network",
    "lastAt": 1762990000000
  }
}
```

Rules:

* **Signed URLs are request-time checked.** `expiresAt` is derived from the
  *final* URL actually used for requests (redirects may land on a differently
  signed URL) using the family's own rule — never `now + TTL`:
  `aws-sigv4`/`gcs-sigv4` = `X-Amz-Date`/`X-Goog-Date` + `X-Amz-Expires`/
  `X-Goog-Expires`; `aws-sigv2`/`generic-expires` = absolute `Expires`;
  `azure-sas` = absolute `se`. A transfer already in flight survives expiry; a
  resume after expiry fails. `signed-url-expiring` therefore means *do not pause*.
  Temporary/STS credentials can expire earlier than the nominal TTL (unknown to
  the client).
* **Resume safety follows RFC 9110 strong comparison.** `range.ifRange` is true
  only when a strong If-Range validator exists (strong ETag; never `W/` or
  Last-Modified-only). `resume.safety`: `strong` = ranges + strong ETag + known
  length; `weak` = ranges + weak ETag/Last-Modified only (resume may work but the
  kernel must not send `If-Range`; it re-probes the validator and validates
  `Content-Range`/length, falling back to a full body on a 200); `none` = no
  usable validator, no ranges, or unknown length. Last-Modified is implicitly
  weak (RFC 9110 §8.8.2.2) and is never `strong`.
* **Checksums are declared availability, not verification.** `crc32c` comes from
  `x-goog-hash`/`x-amz-checksum-crc32c`, `sha256` only from
  `x-amz-checksum-sha256`, `contentDigest` from RFC 9530 `Content-Digest`.
  `verified` stays `null` until a hash is actually compared.
* **Credential redaction is canonical, not cosmetic.** `ServerFacts.url/finalUrl`
  and the `url/finalUrl` fields of `TaskView`/`TaskDetail` are returned with the
  values of credential-bearing query parameters replaced by `<redacted>`
  (`X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`, `Signature`,
  `sig`, `token`, `access_token`, `key`, `api_key`, `secret`, …). The kernel keeps
  the raw URL internally for resume/requests. Request `headers` and `cookie` never
  appear in any protocol view, event, receipt or UI. Task records on disk may
  retain credentials so resume works after a restart; they live only under the
  kernel data dir and are documented as owner-sensitive. The UI redaction is an
  extra layer, never the only one.
* Credential-bearing query values are never repeated in `warnings` or `reason`.
* `warnings` is a bounded set of stable codes:
  `no-range-support`, `no-validators`, `weak-validators`, `unknown-size`,
  `signed-url-expiring`, `signed-url-expired`, `tls-expiring`, `tls-expired`,
  `rate-limited`, `head-failed`, `redirected`, `content-encoding`.
* `recommendation` is a *suggestion*, not an enforced policy. Missing data must
  degrade to safe values (`singleStream: true` when ranges are unknown, never the
  opposite).
* Every optional field is `null`, never omitted, never `""`.

### 2.3 `TaskDetail` (result of `get`)

```jsonc
{
  "telemetry": {
    "windows": { "1s": 1625292, "5s": 1400000, "30s": 1310000, "300s": null },
    "peakBps": 2306867,
    "avgBps": 1200000,
    "stalledMs": 0,
    "trend": "rising" | "steady" | "falling" | "stalled" | "unknown",
    "etaConfidence": "high",
    "samples": 78,
    "lastSampleAt": 1762990000123
  },
  "server": { /* ServerFacts or null before probe completes */ },
  "target": {
    "dir": "C:\\Downloads",
    "path": "C:\\Downloads\\app.zip",
    "part": "C:\\Downloads\\app.zip.part",
    "resumeState": "C:\\Downloads\\app.zip.part.json"
  },
  "verification": {
    "expectedSha256": null,
    "sha256": null,
    "verified": null,
    "serverChecksums": { "contentDigest": null, "contentMd5": null, "sha256": null, "crc32c": null }
  },
  "resumeState": {
    "chunksDone": 0,
    "bytesDone": 0,
    "resumedChunks": 0,
    "resumedBytes": 0,
    "validatorsMatched": true
  },
  "timing": { "queuedMs": 100, "probeMs": 84, "transferMs": 17400, "finalizeMs": 0 },
  "diagnosis": [
    { "code": "on-track", "advice": "wait", "message": "ETA 20s at 5s rate" }
  ],
  "events": [ /* TaskEvent ring, oldest first, caller-bounded */ ]
}
```

`diagnosis` is a bounded list (max 4) of stable codes with machine advice:
`on-track` (wait), `stalled` (inspect-or-restart), `throttled` (wait/lower
connections), `origin-slow` (retry later), `no-range` (single stream, do not
resume), `weak-validators` (avoid resume if remote changes), `checksum-available`
(verify), `signed-url-expiring` (do not pause), `disk-slow` (io wait),
`retrying` (wait), `almost-done` (wait).

`get` returns `{ "task": TaskView, "detail": TaskDetail, "events": [TaskEvent…] }`.
`TaskDetail` is never part of a notification or `list`.

### 2.4 Methods

| method | params | result |
|---|---|---|
| `initialize` | config + `sessionId?` (ignored) | `{protocol,kernel,config}` |
| `probe` | `{url, headers?, cookie?, referer?, userAgent?, proxy?, insecure?, timeoutMs?}` | `{server: ServerFacts}` |
| `start` | `RequestSpec` + `sessionId?` | `{task: TaskView}` |
| `list` | `{status?, sessionId?, limit?}` | `{tasks:[TaskView], aggregate}` |
| `get` | `{id, events?}` | `{task, detail, events}` |
| `wait` | `{ids, timeoutMs?}` | `{tasks:[TaskView], timedOut}` |
| `control` | `{id, action, deletePart?}` | `{task: TaskView|null}` |
| `stats` | `{}` | `{protocol,kernel,tasks:counts,totals,throughput,origins}` |
| `shutdown` | `{}` | `{}` |

`aggregate` (list result):

```jsonc
{
  "total": 12, "active": 2, "paused": 1, "failed": 1,
  "completed": 8, "bytesDownloaded": 918273645,
  "nowBps": 4404019, "w5Bps": 3984588, "w30Bps": 3523215, "w300Bps": null,
  "riskCount": 1   // signed-url-expiring/tls-expired/no-range live tasks
}
```

`stats.throughput` has the same four window fields at kernel level;
`stats.origins` is the number of known hosts.

`RequestSpec` keeps every 0.1 field and adds:

```jsonc
"sessionId": "sess_abc",       // owning agent session; ≤160 chars of [A-Za-z0-9._:-]
"waitProbeMs": 2000            // host-side helper only: max ms to wait for probe; not sent to kernel
```

Time windows: 1s/5s/30s/300s are byte-throughput over the samples available
inside the trailing window, computed from a bounded sample ring (≤ 1 sample /
100 ms, ≤ 3000 samples). A window with fewer than two samples is `null`; a
transfer shorter than a window reports its measured rate in every non-empty
window (the value is the measured rate over the available span, not a claim of
full-window coverage). Paused/idle tasks decay to `0` for `speedBps` and keep
historical windows only until the next sample clears them. `etaConfidence`:
`high` = total known, no stall, ≥5 samples, window CV < 0.35; `medium` = total
known, no stall, ≥2 samples; `low` = total known but unstable/stalling; `unknown`
otherwise.

`recommendation.verify` semantics: `unavailable` = the server declares no
checksum (integrity requires a caller-supplied `expectedSha256`); `recommended` =
the server declares a checksum worth comparing; `required` is reserved for
callers/providers that mandate verification.

### 2.5 Persistence

`TaskRecord` adds `sessionId`, `avgBps`, `peakBps`, `rangeSupported`,
`resumeSafety`, `signedUrlExpiresAt`, `tlsNotAfter`, and the full `server` facts
snapshot (so a completed record can be reviewed after restart). Records written by
0.1.x load unchanged (serde defaults). Origin ledger lives at
`<data-dir>/origins.json`: at most 256 hosts, updated on terminal transition,
atomic replace, ignored when corrupt.

## 3. Model-facing tools (host)

Five tools remain; no new tool is added in 0.2.0. The win is information and
shape, not surface count.

### 3.1 System prompt section (policy lives here, once)

`dsh-rdm:downloads` — ~90 words: use `rdm_*` for every HTTP(S) file download
instead of shell downloaders; `rdm_probe` first when the source is unknown;
`rdm_download` returns a live task; poll with `rdm_wait` (long-poll) rather than
tight loops; the receipts are structured `key=value` lines; do not parse human
prose. Never repeat this policy inside each tool description.

### 3.2 Tool descriptions and parameter notes

Concise behavior + return shape. Parameter rules (`default`, `range`, pairing)
live on the parameter. No repeated policy sentences. Target: the five tool
definitions together stay under the 0.1.2 first-turn token cost despite the richer
outputs.

### 3.3 Canonical outputs

* `rdm_probe` → `{ server: ServerFacts | null, error, hint }`.
* `rdm_download` → `{ task, server, preflightTimedOut, terminal, hint }`, where
  `server` is the preflight `ServerFacts` when it completed within `waitProbeMs`
  (default 2000 ms), else `null`; `preflightTimedOut` describes only that preflight
  wait. `waitSec` still waits for completion (host-clamped ≤300 s) and
  `terminal=true` when the task reached a terminal status inside that wait.
* `rdm_tasks` →
  * list: `{ kernel, tasks, aggregate, counts, hint }` where `tasks` are
    `TaskView` (bounded: default 20, max 100) and `counts` duplicates aggregate
    counts for convenience;
  * with `taskId`: `{ kernel, task, detail, events, hint }` (events max 30).
  * `scope: "session" | "all"` — default `session` when the calling agent has a
    session; agents that need global state pass `all`.
* `rdm_wait` → `{ tasks, timedOut, hint }` (max 20 ids, terminal or timeout).
  The host clamps `timeoutSec` to 300 and always returns a typed `timedOut`
  result rather than throwing when the transfer is simply still running.
* `rdm_control` → `{ action, task, removedId, deletePart, error, hint }`.

### 3.4 Render format (what the model actually reads)

Line-oriented receipt. Stable field order, no JSON punctuation around the whole
value, `key=value` fields separated by single spaces, one record per line,
sections as indented lines. Byte sizes keep binary units; rates use `MiB/s`;
durations are single-unit (`12s`, `3m04s`). `null` renders as `-`. Example
`rdm_download` render:

```
task t_9f3a1c2d5e6b7a80 state=probing session=sess_abc preflight=ok
url https://cdn.example.com/app.zip
server host=cdn.example.com status=200 size=48.1MiB http=HTTP/2.0
range=bytes resume=strong signed=valid(19m40s) tls=valid(40d) checksum=none
plan connections=8 chunk=1.5MiB verify=recommended reason=ranges+strong-etag
next rdm_tasks taskId=t_9f3a1c2d5e6b7a80 | rdm_wait taskIds=["t_9f3a1c2d5e6b7a80"] timeoutSec=60
```

`TaskView` render (list): one line per task:

```
t_9f3a1c2d5e6b7a80 running 42% 20.2/48.1MiB 1.4MiB/s w5=1.3MiB/s eta=20s(high) workers=8/8 range=bytes resume=strong name=app.zip
```

`rdm_tasks taskId` render: a header receipt + `telemetry`, `server`, `target`,
`verify`, `diagnosis`, `events` lines with `-` for unknown.

### 3.5 Recoverable failures are canonical values, not thrown errors

DSH renders any thrown or denied tool call as exactly `Error: <message>`, which
discards structured detail. Therefore all *expected* operational failures return a
normal canonical value carrying `error: {code, message}` and `hint`/`next`
actions, rendered as a receipt line:

```
error code=network message=connection reset by peer
next retry once with rdm_control taskId=... action=retry | inspect with rdm_tasks
```

Only invalid usage (schema violations, unknown arguments, plugin/kernel wiring
faults) throws. `rdm_download` task failures are already canonical (`task.error`);
`rdm_probe` HTTP/network failures, `rdm_tasks` unknown ids, and `rdm_control`
conflicts also return `{error, hint}` values instead of throwing.

The canonical JSON stays available to programmatic callers; render is the model
surface.

## 4. Session attribution and host browser API

### 4.1 Host

* `KernelService.startTask(spec, sessionId?)` sends `sessionId` to the kernel and
  mirrors it.
* Tool execution obtains the session from the tool execution context
  (`exec.agent.session.id`) and passes it; no model-supplied session parameter.
* Every task started before this release (session null) belongs to the global
  view only.

### 4.2 Browser API (`POST /api/dsh-rdm/api`)

Actions: `list` (`{sessionId?, status?, limit?}`), `get` (`{id, events?}`),
`stats` (`{}`), `control` (`{id, action, deletePart?}`). `start` is retained for
tests and programmatic callers but is no longer used by the UI. Envelope
unchanged. `list` returns `{kernel, tasks, aggregate}`.

### 4.3 Review scoping

* Global (left sidebar): all sessions, grouped by `sessionId` (`Global` group for
  null), aggregate strip.
* Session (right sidebar tab): only tasks whose `sessionId` equals the tab's
  session id.

## 5. Kernel algorithm work

1. **Speed ring + windows** (`task.rs` / engine reporter): sample cumulative bytes
   every ≤100 ms into a bounded ring; compute 1s/5s/30s/300s window rates, peak,
   average over active time, stall time, trend and ETA confidence. Reset the ring
   on each run start; keep `peakBps` across pause/resume. No extra wakeups: reuse
   the existing reporter tick.
2. **Probe enrichment** (`probe.rs`): manual redirect chain (≤8, HEAD/GET,
   scheme-safe); TLS leaf certificate validity from `reqwest::tls::TlsInfo`
   (minimal DER walk, no new crates if possible — `nom`/`x509-parser` are not in
   the local cargo cache); signed-URL expiry parser over the FINAL URL (AWS
   SigV4/V2, GCS SigV4, Azure SAS, generic `Expires`/`exp`); checksum headers
   (`contentDigest`/`contentMd5`/`sha256`/`crc32c`); rate-limit headers; warnings;
   recommendation engine; timing (`probeMs`, `ttfbMs`, `sampleBps`).
3. **Resume safety** — derive `strong|weak|none` with RFC 9110 strong comparison:
   `strong` requires a strong ETag (not `W/`) plus ranges plus known length;
   Last-Modified-only is `weak` and never justifies sending `If-Range`. The engine
   sends `If-Range` only for strong ETags; otherwise it re-probes the validator,
   validates `Content-Range`/length, and falls back to a full body on a 200. Store
   the safety and `validatorsMatched` on the task/record and in `TaskDetail`.
4. **Origin ledger** — persist per-host attempts/completed/median/best/last error;
   expose in `probe.origin` and `stats.origins`; bounded 256 hosts, atomic write,
   corrupt file ignored. This is deliberately a *reported history*, not an
   enforced per-origin budget (mirrors/learned concurrency remain non-goals).
5. **Diagnosis** — kernel emits the stable diagnosis codes from §2.3 for live and
   terminal tasks; host passes them through. This replaces the host guessing from
   rates. `signed-url-expiring` always advises "do not pause".
6. **Scheduler / transfer** — no speculative rewrite in 0.2.0. Two measured,
   low-risk adjustments are allowed when benchmarks show a win: coalesce chunks
   only while the pool is saturated (avoid one fast worker hoarding the tail), and
   open the first N range connections only after the first byte of each stream
   lands (avoid a slow-header connection pinning the gate). Any change must be
   A/B measured with `tests/perf.mjs` and documented in `OPTIMIZATION.md`.
7. **Compatibility** — 0.1.x `tasks/*.json` records load; unknown fields default;
   protocol handshake rejects protocol 1 with code `protocol_mismatch`.

## 6. Client UI — "the flight recorder"

Two review surfaces, one visual language. No download composer, no connection
controls, no settings in either surface.

### 6.1 Concept

A download is an **evidence record**: what was asked, what the server claimed,
what the kernel measured, what was verified, what happened over time. The
signature element is the **throughput waveform** (the record's pulse); the second
is the **verification seal** (a compact mark showing expected vs actual hash
state). Everything else is a quiet ledger. One loud element per page: the live
waveform head.

This evolves `.design/DESIGN.md` (the 0.1.x "lane board"): the connection-lane
meter is retired from the review surfaces — the human's question is no longer
"how many lanes" but "what happened and can I trust it". Lane/worker facts remain
as small text data.

### 6.2 Left sidebar entry → global review page (`main`, key `rdm`)

Vertical order:

1. **Ledger header** — title "Downloads", one engine status line
   (`engine v1.1.0 · pid · data dir`), counts (`2 active · 8 done · 1 failed`),
   global rate with 5s/30s windows, and a `risk` marker when any live task has an
   expiring signed URL, expiring TLS certificate or no resume support.
2. **Throughput timeline** — full-width 60–120 s aggregate waveform, light
   fill + line, hour:minute ticks only at the edges, live head dot; the only
   animated element; `prefers-reduced-motion` freezes it. The protocol exposes
   window rates, not a stored series, so the client samples one point per poll:
   the strip is **client-sampled and right-anchored**, labelled as such, and
   shows `—` at the left edge until the window has filled. Never fabricate
   history.
3. **Session-grouped ledger** — groups in recency order: session title (or
   `Unattributed`), one compact aggregate line per group, then records. Each record
   is a row of: status glyph, file name, percent + byte meter (thin, not lanes),
   live rate + 5s window, ETA with confidence marker, host, server chips
   (`range`, `resume`, `signed`, `tls`, `verify`), elapsed. Clicking a row toggles
   an **evidence drawer** beneath it.
4. **Evidence drawer** — request chain, full server facts, timing decomposition,
   telemetry windows, verification block (expected/actual/sha prefix/verified
   verdict, server checksums), destination path, resume state, bounded event log.
   Actions: reveal file, copy path/hash, stop (destructive, requires a second
   click). No other controls.
5. **Empty / error states** — quiet single sentence; no illustrations.

### 6.3 Session right sidebar tab (`sidebar.right.pane.tab`, key `rdm`)

* Registers a native tab **type** `id: "dsh-rdm/downloads"`, kind `rdm`,
  `title: () => t('sidebar.title')`, a guide entry (`order: 40`, title
  "Downloads", description "Reviews this session's downloads"), and the body/title
  slots keyed by the same id. Requires adding
  `@deepseek-ai/dsh-client-ui-sidebar-right` to `dsh.client.inject`.
* Header (sticky): session's active count, aggregate rate, verified count, risk
  count.
* Body: this session's downloads only, newest first: compact waveform per row,
  name, percent, rate, ETA, server chips, seal. Evidence drawer reuses the same
  component as the global page.
* Empty state: "No downloads in this session yet."
* Does not steal focus or auto-open; a guide capsule and inline tool cards are
  the discovery path. (Auto-open is a user preference for later.)

### 6.4 Inline tool cards (stretch, implement if time)

Register `tool.call.toolview` for `rdm_download`, `rdm_probe`, `rdm_tasks`:
compact review rows inside the conversation (name, status, meter, server chips,
seal), expandable to the evidence drawer. This lets a human review without
opening the sidebar.

### 6.5 Visual system

* Host tokens only (`--dsw-alias-*`, `--dsw-specific-*`); dark and light parity;
  contrast ≥ 4.5:1 for text, 3:1 for glyphs.
* Type: host UI stack + tabular numerals; sizes as in `.design/DESIGN.md` (page
  title 20/28, row name 13/20 500, data 12/18). Code font only for paths, URLs,
  hashes, event log.
* Color: live = `state-business-primary`; verified = `state-success-primary`;
  risk = `state-warn-primary`; failure = `state-error-primary`. History rows use
  ink-mixed rails, never full-saturation green/red (the 0.1.x critique).
* Waveform: 1.5px line + 10% fill, no grid; marks at 0/end only; the head dot is
  the only motion. Empty/unknown waveform draws a flat hairline with `—` label.
* Chips: 11px text, 4px radius, 1px border, quiet; at most 4 visible per row,
  overflow hidden (drawer shows all).
* Seals: a bordered capsule with a check/dash glyph, monospace 8-char hash
  prefix, and accessible label; present only when a hash was compared.

### 6.6 Accessibility and states

Keyboard focus visible; row expands with Enter/Space; drawer is a region with
`aria-label`; status glyphs have text alternatives; reduced motion respected;
loading skeleton; per-action error banner; long paths truncate from the left in
the row and wrap in the drawer.
