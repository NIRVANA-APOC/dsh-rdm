# dsh-rdm 0.2.1 — real-data fixes

Status: **design note** for `dsh-rdm` release **0.2.1** (protocol 2, kernel
1.1.0). The frozen interface contract for that pass is kept in the repository
history (`0.2.1` interface spec); this note records *why* each change exists and
the invariants that must hold. Product framing is still
[0.2.0-agent-native.md](0.2.0-agent-native.md).

Scope: kernel (`kernel/src/**`), host TypeScript surface (`src/**`), verification
and docs. All kernel changes are additive; the wire envelope and method set are
unchanged (one new method: `history`).

---

## 1. Why this pass exists

0.1/0.2 were tuned against a **loopback** origin — useful for CPU, write-path and
IPC costs, blind to WAN behavior. The 0.2.1 pass starts from a real
multi-gigabyte download session (ModelScope CDN, kernel 1.1.0) that was exported
on 2026-11-09 and is checked in as the evidence source.

| File | What it contains |
|---|---|
| [`session_logs/20261108/tasks.json`](../../session_logs/20261108/tasks.json) | four task records (one cancelled), plan/server/telemetry/timing/verify fields; Hugging Face same-day baseline |
| [`session_logs/20261108/events.csv`](../../session_logs/20261108/events.csv) | kernel event stream: `probe` / `plan` / `started` / `controller` / `verify` / `completed` / `cancelled` |
| [`session_logs/20261108/telemetry-observed.csv`](../../session_logs/20261108/telemetry-observed.csv) | the only available instantaneous series — sampled **by hand** in the agent session |
| [`session_logs/20261108/README.md`](../../session_logs/20261108/README.md) | the human analysis of the run (root-cause hypotheses, priority list) |

The data's own biggest limitation is one of the fixes: the kernel kept per-sample
telemetry only in memory (`samples=1907` for one task), the MCP projection
exposed aggregates plus a 30-event ring, nothing was persisted. The session
README reconstructed its 8-point series by repeatedly calling `rdm_tasks`; that
is exactly the gap the JSONL recording closes (§5).

Same-machine context (not a 0.2.1 fix, but it shapes the priorities): with the
same client and disk, ModelScope delivered 49.6 MiB/s at 8 connections and
68.5 MiB/s at 16, while Hugging Face gave 1.8–2.4 MiB/s at 8 and 3.6–6.5 MiB/s
at 24. Source choice dominates scheduler tuning; multi-source preflight racing
stays out of scope here (§8).

## 3. Resume: stable identity and decision codes

A stored `.part.json` is adopted only when it still describes the **same
object**, decided from stable identity — never from the raw, tokenized final URL:

* the requested URL;
* the final URL reduced to **scheme + host + port + path** (query and fragment
  dropped);
* the advertised size;
* the validators (strong ETag / Last-Modified).

`TaskDetail.resumeState` reports the outcome explicitly:

```jsonc
"resumeState": {
  "chunksDone": 0, "bytesDone": 0, "resumedChunks": 0, "resumedBytes": 0,
  "validatorsMatched": true,           // boolean
  "resumeDecision": "not-attempted",   // "accepted" | "rejected" | "not-attempted"
  "resumeReason": null
}
```

`not-attempted` means there was nothing to evaluate: it is the pre-plan value and
the outcome of a fresh transfer (with resume enabled) whose `.part.json` does not
exist (a fresh plan is not a rejection). An explicit `resume: false` reports
`rejected`/`disabled`. Any other decision carries one of these codes:

| outcome | `resumeReason` | meaning |
|---|---|---|
| accepted | `etag` | validators matched by ETag |
| accepted | `last-modified` | Last-Modified matched **and** the path identity also matched |
| accepted | `url` | requested URL matched |
| accepted | `final-url` | stable final URL (scheme+host+port+path, no query) matched |
| rejected | `disabled` | resume was disabled for this start; stored state is never adopted |
| rejected | `state-corrupt` | state file present but unreadable / not valid JSON |
| rejected | `version-mismatch` | state format version not understood |
| rejected | `size-mismatch` | advertised total changed |
| rejected | `validators-mismatch` | ETag / Last-Modified changed |
| rejected | `url-mismatch` | neither requested nor stable final URL matched |
| rejected | `file-name-mismatch` | target file name no longer matches the state |
| rejected | `ranges-invalid` | stored ranges are inconsistent with the file |
| rejected | `part-missing` | `.part` file is gone |
| rejected | `part-truncated` | `.part` is shorter than a stored completed range |

Old (0.2.0-format) `.part.json` files still load: missing fields default, and the
stable-identity evaluation decides whether the state is still usable. A rejected
state is not deleted silently — the task restarts from zero and the reason is
reported, so an agent can tell "cancel lost the bytes" apart from "the remote
changed".

Invariants:

* a state is accepted only when identity **and** size/validator evidence agree;
* `resumedBytes` / `resumedChunks` in the view are the plan-time adoption, never
  an estimate;
* a fresh per-request token (`auth_key`, `Expires`, `Policy`, `X-Amz-*`, …) in
  the final URL must **not** change the computed stable identity;
* a genuine remote change (size/validators) must still be rejected.

## 4. Adaptive controller (`kernel/src/controller.rs`)

The requested `connections` stays the **initial population** (and is what
`TaskView.connections` reports). The controller owns `targetWorkers` and may move
it between `1` and `maxConnections`:

| decision | trigger | action | `controller` event example |
|---|---|---|---|
| grow | per-connection rate (`instant / active workers`) is healthy and the transfer is not stalled | raise target by a small step (~⅛ of the current target); never past `maxConnections` | `grow to 24: per-connection 1.8 MiB/s, instant 43.2 MiB/s` |
| revert | the last growth step **diluted** the per-connection rate | restore the previous target | `revert to 16: growth diluted per-connection rate` |
| collapse rebuild | `instant` below 50 % of peak while workers stay pinned (no meaningful stall) | rebuild the HTTP connection pool with fresh TCP/TLS, then grow-probe; revert to the pre-collapse target if the probe does not recover | `pool rebuild #1: 70.4 -> 9.4 MiB/s at 32 workers` |
| backoff | 429/503 or server pushback | halve the target and wait out the cooldown | `backoff to 8: server pushback (429/503)` |
| shrink | average rate falling and the pool is **not** pinned | lower the target by a small step | `shrink to 12: average rate falling` |

The rebuild's follow-up probe emits `grow to N: probe after pool rebuild`; if it
does not recover throughput, the controller emits
`revert to N: pool rebuild and probe did not recover throughput`.

Tuning rationale:

* **Growth is evidence-gated, not periodic**: a step is only taken while
  per-connection throughput shows headroom, so a saturated origin is not
  overloaded with connections that merely re-split the same bandwidth.
* **Growth is reversible**: the previous target is remembered, and dilution of
  the per-connection rate reverts to it. This prevents a ratchet into overshoot.
* **Collapse triggers a pool rebuild, not just more workers**: the real failure
  was *existing* connections collapsing while workers stayed pinned, so adding
  workers onto degraded connections cannot recover it. Fresh TCP/TLS is the
  cheap experiment (no extra payload); new workers then probe whether the origin
  has more headroom.
* **Backoff stays**: server pushback (429/503/`Retry-After`) halves the target
  instead of fighting the origin.
* **Cooldown**: a minimum interval between decisions and the rebuild counter keep
  the controller from oscillating; decisions are logged as `controller` events
  (no new event kinds) and persisted in the event recording.

The decision logic is a pure state machine in `kernel/src/controller.rs`, tested
without a network. `connections` remains the initial population; `targetWorkers`
is the live target shown in `TaskView`.

## 5. Recording (`kernel/src/history.rs`, `history` RPC, `rdm_history`)

Directory `<data-dir>/history/`; one append-only pair per task id:

```
<data-dir>/history/<taskId>.samples.jsonl
<data-dir>/history/<taskId>.events.jsonl
```

Samples are appended at the reporter cadence (≤ 10/s) while a transfer runs,
flushed at least once per second and at terminal transitions; events are
appended as they are retained. Files append across pause/resume/retry/
auto-resume and survive kernel restarts.

Sample line (one JSON object per line):

```json
{"t":1794154378463,"bytes":11596411699,"bps":21893785,"w1Bps":40799331,"w5Bps":27746112,"w30Bps":26249892,"w300Bps":23727081,"workers":16,"peakWorkers":16,"stalledMs":0}
```

Event line (same shape `get` returns, including `controller` decisions):

```json
{"t":1794154378463,"seq":3,"kind":"plan","message":"…","chunk":null,"attempt":null,"delayMs":null}
```

Rules:

* `MAX_RECORDED_SAMPLES = 100_000` per task; on overflow append
  `{"t":<ms>,"truncated":true}` once (the shipped kernel adds
  `"reason":"sample-cap"`) and stop sampling (events continue).
* Event messages pass through `redact_text` before being written.
* Recording failure is advisory: a write error must never fail or slow a
  download.

Read path: `history` RPC
(`{id, offset, limit, raw, includeEvents, eventsLimit}`; `limit` 1..5000 default
500, `eventsLimit` 1..2000 default 200) returns samples plus the retained events
(most recent `eventsLimit`, ring semantics), `samplesPath` / `eventsPath`,
`totalSamples` / `totalEvents`, `truncated`, `sampleStride` and `offset`. The
default view is a bounded review series: when the recording holds more samples
than `limit`, rows are evenly downsampled (first and last kept) and
`sampleStride > 1`; `raw: true` returns a literal page from `offset` instead.
The model-facing `rdm_history` tool reads the same data with a smaller cap
(`MAX_HISTORY_SAMPLES = 2000`, default 300 samples) and renders a bounded
receipt. Unknown task → `not_found`; task with no recording → empty arrays and
`null` paths.

Why this shape: replay is the point. A recorded series is what lets the next
tuning pass reason about growth/collapse without hand-sampling the live session,
and it is the first real-data artifact the next release can compare against.

## 6. Connection cap 128

`MAX_CONNECTIONS` / `DEFAULT_MAX_CONNECTIONS` are **128** in the kernel, the HTTP
pool clamp, `src/config.ts`, `src/protocol.ts`, the tool schema and the docs.
`connections` accepts `1..128`. Task-level `maxConnections` resolves to
`raw.maxConnections ?? initialize.maxConnections`, clamped `[connections, 128]`,
and `singleStream: true` forces both to `1`.

128 is a **safety ceiling, not a default concurrency**: the controller starts at
`connections` (default 8) and only grows while measured per-connection headroom
justifies it. Real runs used 8/16/32; growth needs headroom above the request, so
the ceiling had to move well past 32.

## 7. Tail stall timeout

A pure helper decides the stall budget from progress:

| progress | stall timeout |
|---|---|
| < 90 % | 30 s |
| 90 % ≤ progress < 97 % | 10 s |
| ≥ 97 % | 5 s |

Retries are unchanged; only the timeout before treating a chunk as failed
tightens. The observed worker tail 9→3→2→1 on a 26.4 GiB part is the motivating
case: at the very end a stalled chunk is almost certainly a dead long-tail
connection, so waiting the full 30 s delays the finish for no benefit.

## 8. Invariants

1. **Protocol stays 2.** Every addition is optional or defaulted; old host ↔ new
   kernel and new host ↔ old kernel both remain usable. Kernel identity stays
   `1.1.0`.
2. **Bounds**: `1 ≤ connections ≤ maxConnections ≤ 128`;
   `targetWorkers ≤ maxConnections`; `singleStream` forces 1.
3. **Resume never adopts mismatched bytes.** Size must agree and at least one
   stable identity signal must match (ETag, Last-Modified + same path, requested
   URL, or stable final URL), with a conflicting validator still rejecting. The
   decision and reason are always reported (reason `null` only for
   `not-attempted`).
4. **Controller never exceeds `maxConnections`** and `connections` stays the
   initial population reported in `TaskView.connections`.
5. **Every controller decision is a `controller` event** (grow, revert,
   collapse rebuild, backoff, shrink) and is written to the event recording.
6. **Recording is bounded, redacted and advisory.** A recording error never
   fails or slows a download; the sample series has a hard per-task cap.
7. **Redaction is projection-wide**: raw URLs (including `auth_key`) never appear
   in `ServerFacts`, task views, redirect hops, rendered events or receipts.
8. **Old state loads**: 0.2.0 `.part.json` and task records load unchanged.

## 9. Out of scope for 0.2.1

* **Preflight multi-source racing** — the same-day 10–20× source gap is the
  biggest measured win (the session README ranks it P2), but it is a product
  change, not a kernel-internals fix.
* **Adaptive chunk sizing / proactive tail rebalancing** — only the stall-timeout
  tightening above is in this pass; chunk geometry is unchanged.
* **Binary/compacted resume state** — JSON state remains; large-file scaling is a
  separate performance item (`docs/OPTIMIZATION.md` §7).
