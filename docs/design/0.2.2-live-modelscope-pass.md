# dsh-rdm 0.2.2 — live ModelScope pass

Status: **design note** for `dsh-rdm` release **0.2.2** (protocol 2, kernel
**0.2.2**, unified with the package version). Frozen interface contract: [`.design/0.2.2-spec.md`](../../.design/0.2.2-spec.md).
History: [0.2.0-agent-native.md](0.2.0-agent-native.md) (product framing),
[0.2.1-real-data-fixes.md](0.2.1-real-data-fixes.md) (stable-identity resume,
adaptive controller, JSONL recording).

Scope: kernel (`kernel/src/**`), host TypeScript surface (`src/**`), verification
and docs. All wire changes are additive; the envelope and method set are
unchanged.

Versioning: the previous pass is **0.2.1** (kernel 1.1.0); the 2026-11-09 live
session spanned two 0.2.1 builds that both reported `1.1.0`, which is why this
pass sets the kernel identity to **0.2.2** (same as the package version) and adds build attribution to the
recording. `package.json` is **0.2.2**.

---

## 1. Why this pass exists

0.2.1 and earlier were validated against export/synthetic data. 0.2.2 is the
first pass driven **live**: a real working session on 2026-11-09 downloaded a
model from ModelScope while the kernel's JSONL recording was watched in real
time, the kernel was restarted mid-transfer (resume across builds), and the
observed problems became the change list below. The evidence package is
[`session_logs/20261109/`](../../session_logs/20261109/): kernel-native
`samples.jsonl`/`events.jsonl` (2097 + 376 + 2 rows), the four task records, an
external 2 s sampling series for cross-checking, and the session's own analysis
(`README.md`). The round also downloads
`Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf` (22,360,456,160 B) and
`UD-Q6_K_XL.gguf` (31,843,777,504 B) from `unsloth/Qwen3.6-35B-A3B-GGUF` on
ModelScope into `D:\llm\models` for a larger live measurement (results in §8).

Two facts frame the pass:

* **Source choice still dominates.** The same content is ~0.13 MiB/s on
  Hugging Face (single connection) and 106 MiB/s on ModelScope (16→102
  connections). Multi-source racing remains a roadmap item, not part of 0.2.2.
* **The 0.2.1 fixes worked in the field.** Both restarts resumed
  (`accepted`/`etag`; 2,359,836,648 B, 28,798,211,398 B and 3,676,430,303 B
  adopted, across tasks and builds), the controller grew 16→102 with pool
  rebuild/revert/shrink events, and the kernel recorded ≈6.5 Hz samples to disk.

## 3. History meta and build attribution (`kernel/src/history.rs`)

`<data-dir>/history/<taskId>.samples.jsonl` now starts **each run** with one meta
record before the first sample. A restart, retry or new kernel build appends
another record to the same file, so one file remains one task timeline:

```jsonc
{"kind":"meta","t":1794197622684,"kernelVersion":"0.2.2","pid":1234,
 "taskId":"t_…","run":3,"phase":"plan",
 "url":"<redacted>","fileName":"a.gguf","totalBytes":22360456160,
 "chunkSize":8388608,"chunks":2666,
 "requestedConnections":16,"initialWorkers":16,"maxConnections":128,
 "resumedBytes":0,"resumeDecision":"not-attempted","resumeReason":null}
```

Rules:

* written once per run at plan time, before the first sample; `run` is a
  monotonic 1-based run generation within the kernel process;
* `url` is redacted like every protocol projection; `totalBytes`/`chunkSize`/
  `chunks` are `null` when the plan does not know them (unknown size / single
  stream);
* the reader skips meta lines when counting `totalSamples`/`totalEvents` and
  returns up to `MAX_META_RECORDS = 20` most recent records as `history.meta`;
* the meta record does not count toward `MAX_RECORDED_SAMPLES`;
* 0.2.1-era files without meta remain readable (empty `meta`).

The host projects the records into `rdm_history.builds` (e.g.
`["0.2.2@59852"]`) and adds one `build=` receipt line when they exist, so a
reviewer can see which build produced which slice instead of silently mixing
series from two builds.

## 4. Rate accounting on resume

`Reporter::start(task, counters, total, baseline_bytes)` reports
`transferred = downloaded - baseline` to the rate ring/EWMA/peak while
`downloaded` (absolute) keeps driving progress/percent and the lifetime
`avgBps`. `Task::report` takes both values; the ring baseline is
`transferred = 0` at run start.

Consequences, and the exact real-data symptom they fix:

* `avgBps = downloaded / elapsed` (lifetime, persisted across restarts) while
  245 ms retransfer finished an almost-complete `.part`;
* the first sample/peak of a resumed run are this-run values — no more 8.6/8.8
  GiB/s spikes inherited from the resume jump;
* `TaskView.transferredBytes` exposes the value so a caller can distinguish
  "progress" from "work done by this run";
* `downloaded`, `percent`, `resumedBytes` and verification are unchanged.

## 5. Controller: aggregate growth, saturation, tail freeze

0.2.2 changes only the growth/revert/tail judgement; collapse rebuild and
pushback behavior are inherited from 0.2.1.

| decision | trigger | action |
|---|---|---|
| grow | aggregate throughput shows headroom; transfer not stalled | raise target by a small step, never past `maxConnections`; a probe is kept unless aggregate < 95 % of pre-probe |
| revert | aggregate throughput dropped after a growth probe | restore previous target, **30-tick cooldown** |
| saturation freeze | two consecutive kept growths raise aggregate by < 2 % | stop growing until aggregate < 90 % of frozen peak, or 120 ticks pass |
| tail freeze | `remaining claim units <= target` | hold target: no grow, no shrink, no collapse |
| collapse rebuild | instant < 50 % of peak while workers are pinned | rebuild the HTTP pool with fresh TCP/TLS, then probe growth; revert if the probe does not recover (inherited) |
| backoff | 429/503 / `Retry-After` | halve target (inherited) |

Rationale:

* **Aggregate, not per-connection.** On a saturated line, splitting the same
  bandwidth across more workers temporarily lowers per-connection rate; reverting
  on that produces the 64↔72 oscillation observed live. Aggregate is the quantity
  the user experiences.
* **Saturation is a plateau signal.** When extra workers stop buying aggregate
  throughput, the controller stops probing until throughput actually falls — the
  ceiling is the line, not the worker count.
* **Tail drain is not a slowdown.** Fewer active workers during the last chunks
  is expected; freezing the target removes the bogus shrink, and the fast tail
  retry avoids the observed double 10 s wait on a dead long-tail claim.

Every decision remains a `controller` event with the numbers in the message.

## 6. Receipts, plan and resume-state messages

* `plan` (one stable line):
  `"{total} bytes; chunks={chunks} chunk={chunk_size}; requested={requested} initial={initial} ceiling={max}; resumed={resumed_bytes} bytes resume={decision}"`,
  with `resume={decision}:{reason}` when a reason exists
  (e.g. `resume=accepted:etag`) and `resume=not-attempted` on a fresh transfer.
* `resume state saved`: `"resume state saved: {ranges} ranges / {chunks} chunks / {bytes} bytes"` — ranges are merged ranges, chunks are the chunks those
  ranges cover (computed from the chunk plan), bytes is the on-disk extent.
* `TaskView.requestedConnections` = the caller's `start.connections`;
  `TaskView.connections` remains the initial worker population (may be lower when
  fewer chunks are available).
* `resumeState.chunksDone` reports covered chunks, not merged-range count.
* No tool parameters change; `rdm_history` adds `builds` and the `build=` receipt
  line.

## 7. Unknown RPC method

An unknown method name is no longer an opaque failure: the kernel returns

```jsonc
{"code":"unsupported_method","message":"kernel 0.2.2 does not implement `history`; upgrade the kernel binary (dsh-rdm 0.2.2+)"}
```

so a new host talking to an old kernel gets an actionable error instead of
`unknown method history`.

## 9. Invariants

1. **Protocol stays 2 / kernel identity 0.2.2.** All 0.2.2 additions are
   optional/defaulted; 0.2.1 host ↔ 0.2.2 kernel and 0.2.2 host ↔ 0.2.1 kernel
   remain usable (unknown method now reports `unsupported_method`).
2. **One file = one task timeline.** Meta records make runs attributable; sample
   totals and caps apply to samples only.
3. **`downloaded` is absolute; speed/peak are this-run.** `peakBps`/windows
   never include adopted `.part` bytes.
4. **`requestedConnections` vs `connections`** — the requested count and the
   initial planned population are distinct and both reported.
5. **Controller bounds**: `targetWorkers ≤ maxConnections`; tail freeze only holds
   the target; saturation only stops growth; every decision is a `controller`
   event.
6. **Tail retry is bounded**: 3 s stall deadline, `min(250 ms × attempt, 1 s)`
   delay, max attempts inherited from the transfer's retry budget.
7. **Recording remains bounded, redacted, advisory** (≤100k samples/task, ≤20
   meta records per response).
8. **Old history reads**: 0.2.1-era files (no meta) and 0.1.x task records load
   unchanged.

## 10. Out of scope (documented, not fixed here)

* **Serial post-transfer verification.** 15 s per 26.82 GiB (≈1.8 GB/s) is
  ≈4.4 % of a 339 s transfer; streaming out-of-order chunks into one SHA-256 is
  impossible and a chunk-hash tree would change the verification contract.
* **Multi-source racing.** Still the largest measured win (0.13 vs 106 MiB/s);
  a product-level preflight feature, not a controller fix.
