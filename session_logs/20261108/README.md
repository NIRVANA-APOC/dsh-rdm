## 二、三个可以直接立项的问题

### 1) 续传是坏的（最严重）

三次 plan 事件都写着 `resumed bytes = 0`，而且 `.part` + `.part.json` 都在盘上：

- `t_c613ac42`（16 连接，取消于 29%，10.8 GiB）→ 重启后从 0 开始
- `t_3c58544c`（32 连接）plan 明确 `0 resumed bytes`
- 昨天 HF 那批同样如此（`.part.src` 里存的还是签名 URL）

后果：**取消一次就等于丢掉全部已完成字节**。这也解释了为什么"看起来每次都不接续"。候选根因（待内核侧确认）：

- `.part.json` 的分块表按 `finalUrl`（含 `auth_key` / 签名串）做键，预检后又拿到新 URL，键不匹配就整表作废；
- `cancel` 走的是"丢弃恢复状态"路径，而不是 `pause` 那种保留恢复状态的路径；
- `resume=true` 只在"暂停→恢复"生效，对"取消→重建"无效，但 MCP 侧没有把这个区别暴露出来。

### 2) 单任务吞吐会随时间塌陷

分片1 用 32 连接：`56.9 → 9.3 MiB/s`，同期 `workers` 始终 32/32，`stalled` 只有 130–177 ms（不是卡顿）：

| 时刻(UTC) | 平均 | w30 | peak | workers |
|---|---:|---:|---:|---|
| 16:22:54 | 56.5 | 56.9 | 70.4 | 32/32 |
| 16:35:00 | 38.4 | 9.3 | 71.2 | 32/32 |
| 16:39:00 | 31.2 | 9.4 | 71.2 | 32/32 |

平均 38.4 与 w30 9.3 并存说明是**中途阶跃下跌**，不是平滑衰减。两种可能：服务端按 IP/连接的令牌桶在累计字节后收紧；或者调度器把后续 chunk 全塞给了已经慢下来的连接。可验证的判别实验：同一对象另起 8 连接测一次（若也是 ~0.29 MB/s 量级则是服务端限速；若仍 4 MiB/s 则是内核连接池问题）。

### 3) 内核从不主动加并发

`w5` 已经掉到 9 MiB/s、单连接约 0.3 MiB/s 时，控制器仍维持 32 个 worker 而不做"连接数 × 单连接速率 = 目标吞吐"的重算；反过来在 16 连接时也只做过 16→13→16 的小幅回收。**加并发是我在 MCP 侧手工重启才发生的**（16→32 让吞吐从 20.9 抬到 56.5）。控制器需要一条上探策略：周期性开 k 个试探连接，若每连接速率高于当前均值 x1.3 就保留。

## 三、次要观察

- **固定 8 MiB 分块**：32 连接 × 8 MiB = 256 MiB 在途。恢复不可用的前提下，分块越大，重启损失越大。分块应按"已测单连接速率 × 目标尾延迟"自适应，并随"不可恢复"这一事实一起调。
- **SHA-256 finalize 成本可接受**：26.4 GiB 校验 16 s（≈1.7 GB/s），对 37 GiB 约 24 s。但它在下载完成之后串行执行，建议与最后几个 chunk 的重叠校验一起做。
- **收尾时 worker 阶梯下降**（9→3→2→1）说明尾部 chunk 属于长尾连接，调度器没有对"最后 N 个 chunk"做重试/摘除。
- **小文件比例失真**：mmproj 866 MiB 用 8 连接 16 s 完成（49.6 MiB/s），但 `peak 61.2` 与 `avg 49.6` 的差距说明握手/TLS 成本占比高；小文件应当用更大并发压上去。

## 四、建议的优化优先级

1. **修续传**（收益：任何中断都不再归零；直接决定"敢不敢"取消重来）。
2. **preflight 多源竞速**（收益：10–20 倍，一次探测成本几百毫秒）。
3. **吞吐塌陷检测 + 连接池重建**（收益：本次约 3–6 倍，32 连接阶段从 9 回到 56 MiB/s）。
4. **自适应分块 + 尾部长尾重试**（收益：收尾阶段）。
5. **暴露逐样本 telemetry**（`rdm_tasks` 增加 `samples=all` 或落 JSONL，收益：所有后续调参不再靠外部采样拼凑）。
